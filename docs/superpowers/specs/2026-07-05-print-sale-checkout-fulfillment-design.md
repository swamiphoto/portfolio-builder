# Design: Complete the Print Sale — Checkout, Payment, Fulfillment

Generated by /brainstorming on 2026-07-05
Branch: swamiphoto/run-port-3000
Status: PROPOSED

## Framing

This closes the print-store loop: a site visitor configures a print (existing drawer), enters a shipping address, pays, and **Prodigi prints it and ships it to their door** — with the **photographer as merchant of record via Stripe Connect**, and Sepia intermediating the lab cost. It is the third slice of the print store, after Plan 1 (foundation) and Plan 2 (buyer UI).

It is built **sandbox-first**: Stripe **test mode** + Prodigi **sandbox**, so the entire loop is testable with test cards and non-shipping sandbox orders before any real money or real print. Going live is flipping env keys.

**Multi-tenant from the start** — this platform serves many photographers, so Stripe Connect (not single-merchant) is the model. Swami is photographer #1 who connects an account and places the first real order.

### Implementation phases
1. **Stripe Connect onboarding + checkout** — photographer connects Stripe (Express); buyer enters address, gets a Prodigi shipping quote, pays via Stripe Checkout; an order is recorded. (Prodigi order placement stubbed/sandbox.)
2. **Prodigi fulfillment + tracking** — real Prodigi adapter; the Stripe payment webhook places the sandbox order; a Prodigi webhook updates status/tracking; Orders view; buyer emails.
3. **Go-live** — swap to the production domain (`sepia.photo`, see Dependencies), register production webhooks + Stripe redirect URLs on that domain, flip to live Stripe + Prodigi keys, place a real order.

Each phase produces working, demoable software.

## 1. Photographer onboarding (Stripe Connect Express)

A photographer cannot sell until they connect a Stripe account.

- In admin **Print settings**, a **"Connect payouts"** control:
  - `POST /api/admin/print/connect` → create (or reuse) a Stripe **Express** connected account, return a Stripe **Account Link** → redirect the photographer to Stripe's hosted onboarding (KYC + bank).
  - On return, `GET /api/admin/print/connect/status` refreshes the account's `charges_enabled`; store `stripeConnectAccountId` and `chargesEnabled` in `printStore`.
- The buyer Buy flow activates only when: `printStore.enabled` **and** `chargesEnabled` **and** the image is sellable with available sizes.
- Express is the standard marketplace choice: Stripe hosts onboarding, compliance, and the payouts dashboard — minimal for Sepia to build.

## 2. Buyer checkout flow

From the configured drawer (Plan 2), replacing the placeholder Buy CTA:

1. **Buy this print** → the drawer advances to a **shipping address** step (name, email, address lines, city, state/region, postal code, country).
2. On address entry, `POST /api/print/quote` → server computes `printCost` (Prodigi `getCost` for the spec) and `shippingCost` (Prodigi `getShippingQuote` to the destination) → returns `{ printCost, shippingCost, retail, total }`. The drawer shows **shipping + total**.
3. **Pay** → `POST /api/print/checkout` creates a **Stripe Checkout Session** (see §3) → returns the session URL → the browser redirects to Stripe's hosted checkout.
4. Stripe redirects to `/print/confirmation?session_id=…` (success) or back to the image (cancel). The confirmation page reads the session/order and shows a thank-you + summary. Buyer receives a Stripe email receipt; a shipping/tracking email follows when Prodigi ships.

The drawer owns configuration + address; Stripe owns payment.

## 3. Money mechanics (Stripe Connect direct charge)

At checkout, the server recomputes the quote authoritatively (never trusts client amounts) and creates a **Checkout Session as a direct charge on the connected account** with an application fee:

- Session `mode: 'payment'`, created with `stripeAccount: <connectedAccountId>` (direct charge → the photographer is merchant of record).
- Line items (amounts in the store currency): **the print at `retail`** + **shipping at `shippingCost`**.
- `payment_intent_data.application_fee_amount = printCost + shippingCost + platformFee`.
- `platformFee = round(retail * printStore.platformFeePct / 100)` (0 when the fee is 0).

Resulting split for one sale:
- **Buyer pays:** `retail + shippingCost`.
- **Photographer receives (net, paid out by Stripe):** `retail − printCost − platformFee` (their profit).
- **Sepia receives (application fee):** `printCost + shippingCost + platformFee`; Sepia pays Prodigi `printCost + shippingCost`, keeps `platformFee`.

Invariants: the photographer never fronts lab/shipping costs; Sepia never holds the photographer's profit (only lab-cost + shipping + fee, briefly); the buyer covers shipping. All amounts are integer minor units (cents).

## 4. Fulfillment (Prodigi)

- `common/fulfillment/prodigi.js` — a real adapter implementing the interface against Prodigi's REST API: `X-API-Key` auth, base URL by env (`api.sandbox.prodigi.com` vs `api.prodigi.com`). Maps our `spec` → Prodigi SKUs/attributes; implements `getCost`, `getShippingQuote`, `placeOrder`, `getTracking`.
- `router.getAdapterForCountry` returns the Prodigi adapter (Prodigi ships worldwide; WHCC can be added later behind the same interface for US).
- **Order placement trigger:** `POST /api/stripe/webhook` handles `checkout.session.completed` → verifies the signature → loads the pending order → **places the Prodigi order** (white-labeled to the photographer's brand) → stores `labOrderId` and status. **Idempotent** — keyed on the session id, never double-places.
- **Tracking:** `POST /api/prodigi/webhook` (or a fallback poll) updates the order status → `shipped` + carrier/tracking, and triggers the buyer shipping email.

## 5. Orders & notifications

- **Orders view** in admin (per photographer): a list of orders with status, buyer, spec, amounts (profit), and tracking. Passive — the photographer takes no action to fulfill.
- **Emails:** buyer receipt (Stripe) + a shipping/tracking email when Prodigi ships; photographer notification "you sold a print (+$X profit)." (Email transport: a simple provider — reuse any existing mailer, else a minimal one.)

## 6. Data model

**Order record** — a new per-user GCS store (`users/{userId}/orders/{orderId}.json`, plus an index for the Orders view):

```json
{
  "id": "ord_...",
  "status": "pending | paid | placed | shipped | fulfillment_failed | canceled",
  "assetId": "ast_...",
  "spec": { "size": "16x24", "finish": "lustre", "frame": "wood", "frameColor": "black", "matte": true },
  "buyer": { "email": "...", "name": "...", "address": { "line1": "...", "city": "...", "region": "...", "postalCode": "...", "country": "US" } },
  "amounts": { "retail": 17000, "printCost": 6500, "shippingCost": 1200, "platformFee": 0, "profit": 10500, "currency": "USD" },
  "stripe": { "sessionId": "cs_...", "paymentIntentId": "pi_...", "connectedAccountId": "acct_..." },
  "fulfillment": { "lab": "prodigi", "labOrderId": null, "status": "none", "tracking": null },
  "createdAt": "2026-07-05T..."
}
```

**Site config** — `printStore.stripeConnectAccountId` (exists) + new `chargesEnabled` boolean.

**Env keys** (see §7): Stripe + Prodigi, per environment.

## 7. Setup — the real-account action items (owner: Swami)

Building is sandbox-only and needs no accounts; **going live** requires:

1. **Sepia Stripe platform account** with **Connect enabled** → `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET` (test + live).
2. **Sepia Prodigi account** → `PRODIGI_API_KEY` (sandbox + live).
3. Env in `~/.secrets/<project>.env` (symlinked to `.env.local`) for dev; Vercel prod env for live.
4. **Webhooks:** Stripe → `/api/stripe/webhook` (Stripe CLI `stripe listen` forwards in dev; the live domain in prod); Prodigi → `/api/prodigi/webhook`.
5. **Photographer #1:** connect your Stripe via onboarding, mark an image sellable, enable the store, then place a live order to your own address.

## 8. Architecture / components

- **Server modules:** `common/stripe/client.js` (platform Stripe client), `common/stripe/checkout.js` (build the Connect Checkout Session from an order — pure-ish, testable), `common/print/orderPricing.js` (pure: quote → amounts split, `platformFee`, `profit`), `common/orders.js` (GCS read/write + index).
- **Fulfillment:** `common/fulfillment/prodigi.js` (adapter), `router.js` (return Prodigi).
- **API routes:** `pages/api/admin/print/connect.js` + `connect/status.js` (onboarding); `pages/api/print/quote.js` (Prodigi quote); `pages/api/print/checkout.js` (create session); `pages/api/stripe/webhook.js` (payment → place order); `pages/api/prodigi/webhook.js` (tracking); `pages/api/admin/print/orders.js` (Orders view data).
- **Client:** extend `PrintConfigurator` with an address step + quote display + redirect to Checkout; `pages/print/confirmation.js`; admin **Orders** view + **Connect payouts** control in Print settings.
- Pure amount/split logic lives in `orderPricing.js` and is unit-tested; the Stripe/Prodigi network calls sit behind thin, mockable modules; webhooks are thin and idempotent.

## 9. Out of scope (for now)

Cart / multi-item, discounts/coupons, automated sales-tax (photographer's responsibility; Stripe Tax later), a refunds UI (policy only), the embedded Stripe Payment Element (upgrade from hosted Checkout later), the photoreal wall preview, WHCC/US routing (Prodigi worldwide covers v1).

## 10. Dependencies

- **Domain swap to `sepia.photo` before phase 3.** The build is domain-agnostic (URLs derive from config), but production Stripe/Prodigi webhooks and Stripe redirect URLs should be registered on the final domain once. Do the swap (existing DomainPanel + Vercel tooling) right before go-live.
- **Real Prodigi pricing** surfaces only on an approved account; confirm true costs/shipping before finalizing buyer margins (already noted as the standing print-store blocker).

## 11. Risks

- **Payment succeeds, Prodigi placement fails** → order recorded `paid, fulfillment_failed`, photographer + Sepia alerted, retryable. The buyer already paid, so we retry rather than auto-refund.
- **Connect onboarding incomplete** (`chargesEnabled=false`) → Buy flow stays gated off; the drawer shows "not available yet."
- **Sandbox ≠ live parity** — Prodigi sandbox orders don't ship and its pricing may differ; validate live pricing before real margins.
- **Webhook reliability** — idempotency keys + status reconciliation (poll fallback) so a missed webhook doesn't strand an order.
- **Connect-scoped webhook (launch gate).** Print checkouts are **direct charges on the connected account**, so `checkout.session.completed` fires on the *connected* account, not the platform. The Stripe webhook endpoint MUST be registered as a **Connect** endpoint ("Listen to events on Connected accounts"); locally forward Connect events with `stripe listen --forward-connect-to localhost:3000/api/stripe/webhook`. A normal account-only endpoint never receives these events and every paid order stays stuck at `pending`. The live smoke MUST verify a test-card payment flips the order to `paid`; this is a hard gate before enabling checkout in any environment.

## Success criteria

- A photographer connects Stripe (Express), enables the store, and marks an image sellable — end to end from the admin.
- A buyer configures a print, enters an address, sees a real Prodigi shipping quote and total, pays with a test card, and an order is recorded with the correct amount split.
- The Stripe payment webhook places a Prodigi (sandbox) order; the order shows in the photographer's Orders view; tracking updates on ship.
- Flipping to live Stripe + Prodigi keys (on the production domain) places a real order that prints and ships to the buyer's door.
