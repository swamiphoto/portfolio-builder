# Design: Print Store — Buyer UI (Plan 2, no checkout)

Generated by /brainstorming on 2026-07-04
Branch: swamiphoto/run-port-3000
Status: PROPOSED

## Framing

This is the second slice of the public fine-art print store. Plan 1 (the foundation) built the **photographer side**: marking a library image sellable, resolving sharp print sizes, pricing from a single markup, and a swappable lab adapter with a seeded catalog. It sets a data flag on the image but has no visible effect for a site visitor.

This plan builds the **visible buyer-facing print experience** on the public site — everything a visitor sees and configures — and deliberately stops before money changes hands:

- A subtle "Available as a print" affordance on a for-sale image in the public lightbox.
- An in-lightbox configurator: size → finish → framing.
- A live, in-situ framed preview (the lightbox image itself gains the chosen frame and mat).
- Real prices, computed in the browser from the seeded catalog and the photographer's markup.
- A placeholder "Buy" CTA that Plan 2b will activate.

It is gated behind the store's `enabled` flag so nothing half-finished reaches real visitors.

**Explicitly deferred:**
- **Plan 2b (checkout + payments):** cart/single-item checkout, shipping address, live shipping quote, Stripe Connect, real payment, order records.
- **Plan 3 (live fulfillment):** real WHCC/Prodigi adapters, order placement, webhooks/tracking, Orders view.

## Existing foundation this builds on

- `asset.print` — `{ sellable, masterStorageKey, masterWidth, masterHeight, minDpi, availableSizes, maxSharpSize, focalPoint }` on each library asset (`common/adminConfig.js`).
- `printStore` site config — `{ enabled, markup, showPriceOnImage, currency, stripeConnectAccountId, platformFeePct }` (`common/siteConfig.js`), with `PUT /api/admin/print/settings`.
- `common/print/pricing.js` — pure `lineCost(catalog, spec)`, `computeRetail(labCost, markup)`, `buildPriceMatrix(catalog, sizeIds, markup)`. Import-safe in the browser.
- `common/fulfillment/seedCatalog.js` — `SEED_CATALOG` with `finishes`, `sizes` (with per-finish cost), `frames` (id/label/colors/cost), `matte`. Import-safe in the browser.
- Public site render: `pages/sites/[username]/[slug].js` (`getServerSideProps` reads `siteConfig` + `libraryConfig`, builds `assetsByUrl`), `components/image-displays/gallery/Gallery.js`, and the public image lightbox.

## 1. Data flow

The public page currently builds `assetsByUrl` as `{ [publicUrl]: { assetId, caption } }`. This plan extends it to also carry, per sellable image, the data the buyer UI needs:

```js
assetsByUrl[publicUrl] = {
  assetId,
  caption,
  print: { sellable, availableSizes, maxSharpSize }, // only when sellable
}
```

The page also passes the site's **`printStore`** subset needed by the buyer UI: `{ enabled, markup, currency, showPriceOnImage }`. (Never expose `stripeConnectAccountId` or internal fields to the public page props.)

This threads through `Gallery` → the lightbox so that, for the currently-viewed image, the UI knows: is it sellable, which sizes, and the markup/currency to price with.

**Pricing is computed in the browser.** The buyer panel imports `SEED_CATALOG` and `pricing.js` and computes each option's retail with `computeRetail(lineCost(SEED_CATALOG, spec), markup)`. No new pricing API endpoint. (This ships the seeded catalog to the client bundle, which is intended for v1; Plan 3 will source the catalog from the live lab and may move pricing server-side.)

**Gating:** the affordance and panel render only when `printStore.enabled === true` **and** the image's `print.sellable === true`. With `enabled` defaulting to `false`, real visitors see nothing until the photographer turns the store on.

## 2. Buyer experience

In the public image lightbox, for a for-sale image:

1. A quiet line beneath the image: **"Available as a print"**. If `showPriceOnImage`, it reads **"Prints from $X"** where `$X` is the lowest retail across available sizes (unframed, cheapest finish).
2. Tapping it slides in a **configurator panel** — a side panel on desktop, a bottom sheet on mobile:
   - **Size** — only sizes in `availableSizes` (already resolution-filtered), each showing its price for the current finish/frame selection.
   - **Finish** — Lustre / Matte / Metal (from `SEED_CATALOG.finishes`), as selectable chips.
   - **Framing** — None / Wood / Metal (from `SEED_CATALOG.frames`); choosing Wood or Metal reveals **color swatches** (the frame's `colors`) and a **"With mat"** toggle.
3. The **big lightbox image becomes the live preview** — see §3.
4. A running **total price** for the current `{ size, finish, frame, matte }` selection, computed client-side.
5. A **placeholder CTA**: `Buy this print — $X`, visibly non-active, with a quiet "checkout coming soon." Plan 2b replaces this with the real checkout entry point.

Selecting an unframed option hides the frame color/mat controls. Changing size/finish/frame/mat updates both the price and the live preview instantly.

## 3. Live in-situ framed preview

The preview is deliberately built as a **swappable renderer** so its fidelity can grow over time without touching the configurator or its state. The configurator owns the frame spec `{ frame, frameColor, matte }` and hands it to whatever renderer is mounted.

**v1 renderer — CSS/DOM composite:**

- `components/image-displays/print/FramedImage.js` is the v1 renderer. It wraps the image element and, given the frame spec, renders:
  - an outer **frame band** whose thickness scales with the displayed image size and whose color/material is derived from the selection (wood tones for `wood`, metal grays for `metal`, nothing for `none`), with a subtle bevel/inner shadow for depth;
  - an inner **mat** inset (an off-white border) when `matte` is true;
  - the image inside.
- `common/print/framePreview.js` — a **pure** helper mapping `{ frame, frameColor, matte }` → the concrete style values (frame band thickness ratio, border color, bevel, mat thickness/color). Unit-testable, no DOM. `FramedImage` consumes it.

This v1 preview is an approximation for configuring intent; it does not promise the exact product photo. No canvas, no external image generation, lab-agnostic.

**Eventual direction — photorealistic "see it on your wall" (NOT built in v1):**

The goal is a preview compelling enough to entice the purchase — the print shown realistically framed, ideally staged on a wall at true scale, rather than a flat CSS frame. The renderer boundary above is what makes this a drop-in later. Options to evaluate when we do the Plan 3 lab integration:

- **Lab mockup/preview API** — if the chosen lab (WHCC/Prodigi/etc.) exposes a mockup or product-preview generator, use it to render the real framed product. WHCC has an embeddable Editor API; POD labs commonly offer mockup generation. Confirm capabilities during Plan 3 lab onboarding.
- **Room/wall visualization** — composite the framed print into a staged room scene (or a wall photo the visitor uploads) at true physical scale, so they see it "on their wall."
- **Higher-fidelity local composite** — realistic frame textures, shadows, and glass reflection as an interim step short of a full API.

This is a tracked future enhancement, not part of this plan; v1 ships the CSS renderer behind the swappable boundary.

## 4. Photographer side

- **Enable toggle + markup + show-price**: a compact **Print settings** control surfaced in the admin site settings (matching the sidebar-driven editing invariant), wired to the existing `GET/PUT /api/admin/print/settings`. It exposes `enabled` (the gate), `markup`, and `showPriceOnImage`. This is the mechanism the photographer uses to turn the buyer experience on and to preview it.
- No change to the per-image "Sell as print" panel from Plan 1 (already shipped).

## 5. Components and modules

- `common/print/framePreview.js` — pure frame/mat style resolver.
- `common/print/buyerPricing.js` (thin) — buyer-facing helpers over `pricing.js`: `startingPrice(catalog, availableSizes, markup)` (lowest retail for the "from $X" line) and `optionPrice(catalog, spec, markup)`. Keeps price logic in one testable place.
- `components/image-displays/print/PrintPurchasePanel.js` — the configurator (options, live price, placeholder CTA). Presentational; receives `{ print, printStore }` and a `spec`/`onSpecChange`.
- `components/image-displays/print/FramedImage.js` — the v1 (CSS) live framed preview renderer, mounted behind a swappable boundary so a photorealistic renderer (lab mockup API / wall visualization) can replace it later without changing the configurator (see §3).
- `components/image-displays/print/PrintAffordance.js` — the subtle "Available as a print" line that opens the panel.
- Public render wiring: extend `assetsByUrl` in `pages/sites/[username]/[slug].js` (and `index.js` if it renders galleries), thread `print`/`printStore` through `Gallery` to the lightbox, and mount the affordance + panel + framed preview there (gated by `enabled` + `sellable`).
- Admin: a Print settings control (enable + markup + showPriceOnImage) in site settings.

Each unit has one responsibility: `framePreview`/`buyerPricing` are pure and tested in isolation; `FramedImage`/`PrintPurchasePanel`/`PrintAffordance` are presentational; the public-render wiring is the only integration surface.

## 6. Out of scope

- Cart and checkout, shipping address, shipping quotes.
- Stripe Connect, payment, order creation, order records.
- Real lab fulfillment, webhooks, tracking, Orders view.
- Per-image price overrides, digital downloads.
- Photoreal frame rendering; exact product photography.
- Mat color choice (mat is on/off, matching Plan 1's catalog).

## 7. Open risks and constraints

- **Which public lightbox.** The public render uses a URL-string-based lightbox (`components/image-displays/lightbox/Lightbox.js`) plus the `Gallery` component's own lightbox handling (`?photo={index}`). The implementation plan must confirm the exact component the `Gallery` drives on the public site and attach the affordance/panel/framed-preview there. This may require passing richer per-image objects (with `print` data) into that lightbox rather than bare URLs — a small, contained refactor.
- **SSR prop size.** Threading `print` data for many images inflates the page props. Only attach `print` for sellable images, and only the three fields needed.
- **Catalog in the client bundle.** Shipping `SEED_CATALOG` to the browser is intended for v1. When Plan 3 sources a live catalog, revisit whether pricing moves server-side.
- **Preview fidelity.** A CSS frame is an approximation; acceptable for configuring intent in v1. The eventual goal is a photorealistic "see it on your wall" preview to drive conversion (§3); v1 builds the renderer behind a swappable boundary so that upgrade is a drop-in, and the lab-mockup-API option is evaluated during Plan 3 lab onboarding.

## 8. Success criteria

- With the store enabled, a visitor opens a for-sale image, sees "Available as a print," opens the panel, and picks size/finish/frame/mat — with the lightbox image showing the chosen frame and mat in place and a correct price updating instantly.
- With the store disabled (default), no print UI appears anywhere on the public site.
- The photographer can enable the store, set a markup, and preview the whole buyer experience without any payment infrastructure existing.
