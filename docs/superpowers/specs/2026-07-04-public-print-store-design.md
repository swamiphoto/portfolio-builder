# Design: Public Fine-Art Print Store (v1)

Generated by /brainstorming on 2026-07-04
Branch: swamiphoto/run-port-3000
Status: PROPOSED

## Framing

Payments and selling in this platform is not one feature — it is **two storefronts sharing one commerce and fulfillment engine**:

- **Public print store** (this spec) — a site visitor buys a framed or unframed fine-art print of any image the photographer has marked for sale. It ships to their door.
- **Client delivery** (a later spec) — private galleries delivered to a specific client (e.g. a wedding), offering digital downloads, prints, packages, and discounts.

Both storefronts plug into the same core: marking an image sellable, resolving the print master, pricing, Stripe payments, and print-lab fulfillment. We build that core here, behind the public store, and reuse it for client delivery later.

This spec covers the public print store only. Client delivery is explicitly out of scope (see §11).

## Existing scaffolding

The page model already reserves fields we will use or supersede:

- `page.clientFeatures.purchase` — `{ enabled, defaultPrice, currency, tiers: { web, print, original } }` (placeholder, unused).
- `asset.forSale` — boolean flag on library assets (placeholder, unused).

Nothing is wired behind these. There is no Stripe, checkout, fulfillment, or high-resolution handling today. We design from a clean slate and reuse the reserved field names where they fit.

Relevant existing infrastructure we build on:

- Per-user GCS/R2 storage with JSON config helpers (`downloadJSON` / `uploadJSON` in `common/gcsClient.js`).
- Library asset model (`common/adminConfig.js`, `createAssetRecord`) — each asset already stores `width`, `height`, `aspectRatio`, `publicUrl`, `storageKey`.
- NextAuth Google OAuth with per-user isolation (`session.user.id`, `common/withAuth.js`).
- The public-site lightbox (`components/image-displays/lightbox/Lightbox.js`) — the natural anchor for the buy affordance.
- Sidebar-driven editing invariant: all edits are initiated from the admin sidebar; the preview is theme-dependent and read-only; stored data is theme-independent.

## 1. What a buyer can order

A **curated catalog**, not a configurator. For any sellable image the buyer chooses:

- **Medium / finish** — a small curated set, e.g. Lustre paper, Matte paper, Metal. 2–3 options.
- **Size** — standard print sizes, automatically filtered to only those the image's resolution can print sharply (≈240 DPI floor). Sizes the image cannot support are never shown.
- **Framing** — None / Wood / Metal, plus:
  - **Frame color** (from the lab's available colors)
  - **Matte** — with or without (v1: a simple white mat on/off; mat color is a later addition)

The exact option list is finalized against the chosen lab's real product catalog — the fulfillment adapter (`getCatalog`) exposes actual products, sizes, frames, and mat options, so we never offer a combination the lab cannot make.

Digital downloads are **not** part of the public print store (they belong to client delivery). This store sells physical prints only.

## 2. Library: mark for sale and the print master

Everything is initiated from the library, per the sidebar-driven editing invariant. No per-page setup.

Flow when the photographer selects an image and chooses **Sell as print**:

1. The system reads the asset's stored `width` / `height` and computes the largest size that prints sharply at the ~240 DPI floor.
2. It states the result plainly, e.g. *"Prints sharply up to 16×24. Upload a higher-resolution file to offer larger sizes."*, with a drop zone right there.
3. **Use what's there when it is big enough.** If the existing original already supports the sizes the photographer wants, no upload is required. A separate print-master upload is prompted only when the current file is too small.
4. Sizes beyond the quality threshold are hidden, so a buyer can never order a print that will look soft.
5. The image is now sellable at every size it can support. Available sizes are cached on the asset.

**Print master** is stored as a distinct high-resolution file reference when uploaded, separate from the web/display/thumbnail variants. When no separate master is uploaded, the original upload serves as the print master.

**Aspect ratio and cropping.** Standard print sizes have fixed ratios that rarely match the camera frame, so something must be cropped. v1 offers **all standard sizes** and applies a **focal-point auto-crop** (using any focal point already on the asset, else center), which the buyer can **nudge at checkout**. We do not restrict sizes to the native ratio.

**Known limitation:** we detect resolution, not sharpness. A large-but-soft file could still print poorly. v1 accepts this.

## 3. Pricing: one global markup

The photographer sets a **single number** — a markup multiplier or target margin — pre-filled with a sensible default. Every retail price across the entire size × finish × frame matrix is computed automatically from the lab's cost. The photographer can review the resulting price list before publishing but never types individual prices.

Per-image price overrides are **out of v1**. The reserved `page.clientFeatures.purchase` tier fields are superseded by the print-store markup model described here.

## 4. Buyer experience

**On the image only.** No dedicated shop page feature. A photographer who wants a storefront simply builds a normal page/gallery of buyable images using the existing page model.

- In the public-site lightbox, a **subtle affordance** appears for sellable images: *"Available as a print"*, with an optional **show-price** toggle (per-site). Fine-art sensibility — no loud "BUY NOW".
- Tapping it opens the **print picker**: size → finish → framing (frame / color / matte).
- **Live preview.** As the buyer changes options, the image re-renders inside the selected frame and mat in real time. This is our **own client-side composite** (image + frame + mat), not a lab's embedded editor — instant, and lab-agnostic so it works identically whether the order routes to WHCC or Prodigi.
- **Crop adjust.** When the chosen size crops the image, the buyer sees the auto-crop and can nudge it.

**Checkout — single item, no cart.** Someone who wants multiple prints buys them separately.

1. Buyer confirms options and crop.
2. Buyer enters shipping address.
3. We fetch a **live shipping quote** from the routed lab for that destination.
4. Buyer pays (Stripe).
5. Buyer receives an **email receipt**, then a **shipping/tracking email** when the lab ships.

## 5. Fulfillment

A thin **fulfillment adapter** interface abstracts the print lab:

- `getCatalog()` — products, sizes, frames, mats, finishes.
- `getCost(spec)` — lab cost for a given print spec.
- `getShippingQuote(spec, address)` — shipping cost and ETA to a destination.
- `placeOrder(spec, address, branding)` — submit a white-labeled order, return lab order id.
- `getTracking(labOrderId)` — status and tracking (also received via webhook).

**Two adapters, routed by destination:**

- **US → WHCC.** Top fine-art/metal quality with a modern self-serve REST API, sandbox, webhooks, framing (including mats) in the API, and unbranded drop-ship (~$7.95/order). North-America-centric, which is fine for the US route.
- **Worldwide → Prodigi.** Global local-production network (auto-routes to the facility nearest the buyer), simple API-key auth, sandbox, catalog-by-SKU, full white-label, and the richest API-driven framing (8 frame colors + glaze/mount options).

Bay Photo (premium ChromaLuxe metal, but partner-gated API, no sandbox) and theprintspace / creativehub (museum-grade fine-art, self-serve API) can slot in later behind the same interface. Routing is a config detail, not an architectural fork.

Behavior: a paid order flows **straight to the lab automatically**, white-labeled so the package arrives as the photographer's brand. Tracking syncs back via webhook and appears in the Orders view. **No photographer approval gate** — the buyer confirms the crop at checkout, so a gate would add friction without value.

## 6. Money — Stripe Connect

- The photographer connects their **own Stripe account** during setup and is the **merchant of record** for the retail sale.
- **Sepia holds the single lab account.** These labs integrate as one platform account, not one account per photographer. So Sepia intermediates the lab cost through Stripe's application fee.
- **Per-sale money flow (Stripe Connect):**
  - Buyer pays the full retail price on the photographer's connected account.
  - Stripe's **application fee = lab cost + Sepia's platform fee**, captured to Sepia.
  - The **remainder (the photographer's profit) settles to their connected account.**
  - Sepia pays the lab out of the collected application fee.
- **Net effect:** the photographer **never fronts lab costs**, Sepia **never holds the photographer's profit** (only lab-cost + fee, briefly), and the photographer's profit lands automatically.
- **Sepia's platform fee** is a single configurable percentage, defaults low, and can be set to **0%** so "sell your prints, keep (almost) all of it" stays available as a pitch.
- **Refund policy (not a build):** because orders hit the lab immediately, refunds are clean only *before production starts*. After production begins it is the photographer's call. Documented as policy for v1.
- **Sales tax** is the photographer's responsibility as merchant of record. v1 does not compute tax. Stripe Tax can be added later.

## 7. Setup and Orders (photographer side)

**Setup** (from admin, sidebar-driven):

1. Enable selling.
2. Connect Stripe (Connect onboarding).
3. Set the global markup.
4. Done. Marking individual images happens in the library (§2).

**Orders view** in admin: every order with its status, buyer, the print spec, profit, and tracking. Fully passive — the photographer takes no action to fulfill.

**Notification** on each sale: *"You sold a print (+$X profit)."*

## 8. Data model

**Asset extension** (library asset record) — a `print` object:

```json
{
  "print": {
    "sellable": true,
    "masterStorageKey": "users/{userId}/photos/print-masters/{filename}",
    "masterWidth": 6000,
    "masterHeight": 4000,
    "maxSharpSize": "24x36",
    "availableSizes": ["8x10", "11x14", "16x24", "24x36"],
    "focalPoint": { "x": 0.5, "y": 0.42 }
  }
}
```

`asset.forSale` (existing reserved boolean) mirrors `print.sellable` for back-compat.

**Site / user config** — a `printStore` object:

```json
{
  "printStore": {
    "enabled": true,
    "markup": 2.5,
    "showPriceOnImage": false,
    "currency": "USD",
    "stripeConnectAccountId": "acct_...",
    "platformFeePct": 0
  }
}
```

**Orders store** — a new per-user GCS JSON store (`users/{userId}/orders-config.json` or per-order objects), one record per order:

```json
{
  "id": "ord_...",
  "assetId": "ast_...",
  "spec": { "size": "16x24", "finish": "lustre", "frame": "wood", "frameColor": "black", "matte": true, "crop": { "x": 0.5, "y": 0.42, "zoom": 1.0 } },
  "buyer": { "email": "...", "shippingAddress": { } },
  "payment": { "stripePaymentIntentId": "pi_...", "retail": 180, "labCost": 70, "platformFee": 0, "profit": 110, "currency": "USD" },
  "fulfillment": { "lab": "prodigi", "labOrderId": "...", "status": "in_production", "tracking": { "carrier": "...", "number": "...", "url": "..." } },
  "createdAt": "2026-07-04T..."
}
```

## 9. Component and module shape

- **Fulfillment adapters** — `common/fulfillment/` with an adapter interface plus `whcc.js` and `prodigi.js`, and a `router.js` that selects the lab by destination country.
- **Pricing** — a pure module that turns lab cost + markup into the retail matrix.
- **Print-size resolver** — a pure module computing `maxSharpSize` / `availableSizes` from pixel dimensions.
- **Library "Sell as print" UI** — sidebar panel + print-master drop zone.
- **Print picker + live preview** — public-site component opened from the lightbox; client-side frame/mat compositor.
- **Checkout** — single-item flow with shipping-quote fetch and Stripe payment.
- **Orders API + Orders admin view** — read orders, receive lab webhooks, update status.
- **Server API routes** under `pages/api/` for: enabling the store, Stripe Connect onboarding, price/shipping quotes, creating a payment + order, and lab webhooks.

Each unit has one purpose and a defined interface; the lab adapters and the pricing/resolver modules are independently testable.

## 10. Out of v1

- Client delivery / private galleries, digital downloads, packages and discounts.
- Per-image price overrides.
- Cart / multi-item checkout.
- Dedicated shop-page feature (photographers build one from a normal page).
- Photographer approval gate before fulfillment.
- Automated sales-tax calculation.
- Mat color choice (mat is on/off only in v1).
- Bay Photo and theprintspace adapters (interface supports them; not built in v1).

## 11. Open dependencies and risks

- **Real lab pricing is gated behind approved accounts.** We need a WHCC account and a Prodigi account to pull true per-item cost and shipping before finalizing buyer-facing margins. This is the main external blocker to shipping.
- **Fine-art fidelity across global production hubs** (Prodigi) is less controllable than a single US lab. Acceptable for the worldwide route; worth monitoring for a fine-art brand.
- **Resolution ≠ sharpness.** A large but soft print master can still print poorly; v1 does not detect this.
- **Refunds after production** have no clean automated path in v1; handled by policy.

## Success criteria

- A photographer enables selling, connects Stripe, sets one markup number, and marks an image sellable in under 5 minutes.
- A site visitor buys a framed print, sees an accurate live preview, pays, and the order reaches the lab automatically with zero photographer action.
- The photographer sees the order, its profit, and tracking in the Orders view without touching fulfillment.
